## Stage 2: Storage, egress and assembly adapters — ✅ done

- [x] **5. Storage adapter extension**
- [x] **6. Egress client**
- [x] **7. Audio assembler**

**Observations:**
- `StorageService.statObject` distinguishes a missing object (`null`) from an unreachable store (thrown `StorageUnavailableError`) by checking the S3 SDK error's `name === 'NotFound'` or `$metadata.httpStatusCode === 404`; anything else is treated as unavailable. `objectExists` is left untouched (still collapses every failure to `false`) since nothing yet depends on changing its behavior and the spec's assumption explicitly contrasts the two rather than asking for one to replace the other.
- `uploadFile`/`downloadToFile` buffer through `fs/promises` rather than streaming — a **deviation** from the plan step's "stream files up and down" wording, recorded here: every current caller uploads or downloads an assembled lesson recording, bounded by the 120-minute lesson cap (well under 50 MB at F07's mono 48 kbps Opus), so this matches `getObject`/`putObject`'s own already-buffered style rather than adding chunked-upload machinery (S3 multipart, content-length negotiation) for a file size that never needs it.
- `deleteObjects` uses a single `DeleteObjectsCommand` rather than looping `deleteObject`, matching the plan's "delete in bulk" wording; a no-op guard on an empty array avoids S3's own rejection of a zero-object delete request.
- `EgressService` mirrors `LiveKitService`'s own discipline: every call wrapped, every transport failure translated into a typed `EgressUnavailableError` that never leaks the raw SDK message. `DirectFileOutput`'s `disableManifest: true` matters beyond tidiness — egress otherwise uploads a `.json` manifest alongside the media file, which would break the finalization criterion "every object under this lesson is audio".
- **Found and fixed a genuine bug while manually exercising `AudioAssembler` (not just a test bug):** the first version relied on `-t <duration>` as an output option to force the assembled file's length, on the assumption it would pad a short mix the way it trims a long one. It does not — `ffmpeg -t` only trims; `amix` stops emitting the moment its longest *input* stream ends, so a segment whose own decoded audio is shorter than its declared wall-clock span (the exact case F07 exists to handle — a mute near the end of a segment) silently truncated the whole output instead of being silence-padded. Fixed by adding `apad=whole_dur=<seconds>` on the mixed stream before the final `-t` safety trim. Caught by generating two synthetic Opus tones with `ffmpeg`'s own `sine` source and running the real `AudioAssembler` class against them via `tsx` (not a reimplementation) with three cases — a real inter-segment gap, an intra-segment shortfall, and a single segment — then reading back each output's per-second volume levels (`-af volumedetect` over narrow `-ss/-to` windows) to confirm tone/silence placement and duration, not just trusting the reported `durationMs`. Also confirmed `amix`'s `normalize=0` avoids the volume attenuation `amix` applies by default (would have quietly halved loudness per extra segment, since segments never overlap and summing them is exactly concatenation, not simultaneous mixing).
- Manually exercised `EgressService`'s real request shape against the running `egress`/`livekit` containers (a fake track id against a real, then a nonexistent, room) — confirmed the server accepts the `DirectFileOutput`/`S3Upload` construction (a specific, meaningful LiveKit error — "requested room does not exist" — rather than a malformed-request rejection) and that a failed/incomplete egress leaves no stray object or manifest in MinIO. Full success (a real published track actually uploading a segment) needs Stage 3's live wiring plus a real WebRTC call, which this environment cannot run standalone; recorded as the natural continuation, not a soft-fail of Stage 2's own scope.
- `ffmpeg-static` added as a direct dependency of `apps/api`; resolves and runs correctly on the host (Windows) — the container install is deferred to whichever stage next runs `docker compose exec api pnpm install`, since nothing in Stage 2 runs inside the container yet.
- No new automated test files in this stage — `storage.spec.ts`, `egress.service.spec.ts` and `audio-assembler.spec.ts` are explicitly Stage 5's own step (21) per the plan, matching F05/F06's precedent of a dedicated late test-suite stage. Stage 2's manual exercises above are a substitute for "actually run it" now, not for the formal suites later.

**Observations:**
- `recording-classifier.ts` is a pure function module (no injectable, no I/O) — checked by hand against every scenario in the spec's own test table (complete, partial ≥/< 3 min, failed-to-start, no segments, object ≤ 10 KB, assembly error, plus all four `deriveLessonStatus` cases) via a throwaway script before writing the finalizer around it; all 18 checks passed on the first try.
- **Stored `recording_status` vocabulary is coarser than the failure-code vocabulary, by design and matching the spec's own example response:** `too_short`/`assembly_failed`/`missing-object` outcomes all persist as `lesson_participants.recording_status = 'missing'` — the schema's 7-value enum has no room for a fourth distinct failed-participant status, so `failureCode`/`failureReason` on the branch carry the specific reason, and `recordingStatus` on the participant is deliberately the coarse bucket. `failed_to_start` is the one failure that keeps its own distinct stored value, because it is already the correct terminal value the live orchestrator wrote — finalization confirms it rather than remapping it.
- **Deviation, a real bug found and fixed by manual verification, not by a written test:** the first version of the assembly loop called `StorageService.downloadToFile` directly on every `complete` segment, trusting that a segment marked complete always has a real object. Manually running the finalizer against real leftover test data from F05/F06 (lessons that predate F07 and were correctly picked up by the finalization scan, see below) surfaced a segment whose object genuinely didn't exist, and `downloadToFile`'s underlying `getObject` doesn't distinguish "missing" from "unavailable" the way `statObject` does — the resulting plain error was neither a `StorageUnavailableError` (so it didn't defer for the storage-outage retry) nor caught anywhere else, so it propagated up, got logged and swallowed by the job's per-lesson try/catch, and the *same* lesson was re-claimed and re-thrown every 5-second tick forever. Fixed by calling `statObject` first for every segment about to be downloaded: a `null` (missing) result drops that one segment from the assembly (contributing nothing, exactly as if it had never existed) instead of throwing, while a thrown `StorageUnavailableError` still propagates to the intended storage-outage path. A participant left with zero usable segments this way is classified `recording_missing`, same as if no segment had ever been created.
- **Deviation, resolving a real correctness risk found while designing the retry-across-participants case:** a participant whose branch already reached `queued` (`launched_at` set) is skipped entirely on any later finalization pass — no re-download, no re-classification. This is necessary, not just an optimization: their segment *objects* are deleted from storage once verified (per the spec's "then deletes the segments"), so a retry triggered by a *different* participant's failure would otherwise try to re-download objects that no longer exist. The database *rows* for those segments are kept forever (never deleted) — matching `LessonRecordingSegment` having no deletion path of its own in the spec's data model, and giving the settle/reconcile step and any future audit an unbroken history regardless of what storage does with the underlying files.
- The finalizer computes every participant's classification and audio object in memory first (`assembleAll`), and only writes anything to the database (`commit`) once the whole lesson's assembly pass completes with no storage failure — so a mid-lesson storage outage on participant B never leaves participant A's already-uploaded, already-verified audio uncommitted while also being unable to retry it (A's object simply stays in storage, uncommitted, and gets correctly picked up on the next tick).
- `RecordingFinalizationJob` follows `LessonLifecycleJob`'s exact pattern: one lesson's `finalize()` throwing is caught, logged and released (never stops the sweep over the rest); state lives entirely in Postgres (the lease), so an API restart mid-finalization loses no progress.
- `too_short`'s audio-is-still-stored rule (PRD Error Handling is silent on this specific point beyond the lesson-history experience text) is honoured by running the full assemble-and-verify step for every connected participant *before* checking the lesson's own duration — the duration check only ever decides whether branches and seams follow, never whether audio gets assembled and uploaded.
- `RecordingController`'s routes live under `lessons/:lessonId/recording`, a path NestJS routes independently of which module declares the controller — `RecordingModule` registering it does not require `ClassroomModule` (or anything else) to import anything new.
- `docs/api/openapi.json` regenerated (19 operations now, up from 17: the two new recording routes; `HealthReport`'s dependency enum gains `egress`).
- **Pre-existing test fixed, not written new:** `apps/api/test/integration/health.spec.ts`'s `reports_every_dependency_with_latency` hard-coded the sorted dependency-name list; added `'egress'` to it. This is the one existing-test change this stage needed, not a new suite (health's own dedicated coverage is otherwise Stage 5's `test/integration/health.spec.ts` extension, already in place from F01/F05).
- **Manual, real-stack verification, more extensive than planned because the running dev server surfaced the bug above on its own:**
  - With the finalization job running continuously against the live stack (its normal `@Interval`, not a one-off script), it autonomously swept up **fourteen pre-existing lessons left over from F05's and F06's own manual verification** — lessons that predate F07 entirely and had `recording_status = 'idle'` only because the migration defaulted every existing row. Ten reached `too_short` (most had never actually started, `duration_seconds` null; one had a genuine 24-second `duration_seconds`) with **zero branch rows created for any of them**, confirmed directly in Postgres. Two reached `recording_failed`, each with two `recording_missing` branches (both participants had genuinely published no microphone in those pre-F07 sessions) and a fallback plan correctly requested for both.
  - This is what surfaced the missing-object bug above — one of those lessons' rows happened to look, by coincidence of unrelated earlier manual testing, like a `complete` segment with no real object, wedging it in an infinite retry loop until the fix landed; confirmed the loop stopped and the lesson finalized correctly (`recording_failed`, `recording_missing`) once the fix was live.
  - Exercised `GET /lessons/:lessonId/recording` for real against one of those `recording_failed` lessons: response shape, values and the branch object all matched the spec's contract exactly (`recordingStatus: "missing"`, `failureCode: "recording_missing"`, `retryable: true`, `fallbackPlanRequested: true`).
  - Exercised the full **retry cycle end to end**: `POST .../recording/retry` returned 202, moved the lesson to `finalizing` and both branches to `verifying`; the next tick (5 seconds later, the real scheduled interval, not a forced run) reprocessed both participants from scratch and converged back to the identical `recording_failed` outcome — `attempts` incremented from 1 to 2 on both branches, and `fallback_requested_at`'s timestamp was **unchanged**, proving the seam is not called a second time across a retry.
  - Exercised the error paths for real: a malformed lesson id → 400 `VAL001`; no session → 401 `AUTH003`; retrying a `too_short` lesson (no branches at all) → 409 `REC001` with `details.recordingStatus: "too_short"`.
  - `REC002` (retry while still capturing/finalizing) was not separately exercised live — every lesson available in the local database was already terminal by this point in the run; its logic is a direct, simple guard shared with no other new code path, and is covered by the formal suite in Stage 5.
  - Cleaned up the one stale lesson row this session had itself created earlier (Stage 3's fabricated-webhook smoke test, never a real recording) rather than leaving it to the fix; the other fourteen were left as genuinely finalized historical data, since they are real product history from earlier features, not scratch state.
